## GESTURE ROOT CAUSE

`Viewport.kt` kept `previousCentroid` and `previousSpread` across a change in
the pointer set. When a second finger landed, the next frame compared the
two-finger centroid with the one-finger position (a pan of half the finger
distance) and the new spread with 0 or the old spread (a zoom). The reverse on
lift. The travel accumulator also mixed pan and spread change, and the orbit
gain was per pixel (0.32°/px: 346° per width at 1080 px, 461° at 1440 px).

## GESTURE REDUCER

`apps/android/app/src/main/java/com/buildplan/preview/camera/CameraGesture.kt`:
`CameraGestureTracker`, a pure state machine (no Android or Compose import).
Samples in (`Frame(pointers with ids, timeMs, width, height, density)` or
`Cancel`), semantic actions out (`Began, Orbit(dYaw, dPitch), Pan(right, up in
viewport heights), Zoom(scale), Tap, DoubleTap`). `Viewport.kt` only
translates Compose events into samples and actions into the existing view-model
calls; a system cancel (all pointers released at once, already consumed) is
recognised as `Cancel`.

## POINTER REBASE

Whenever the ordered list of pressed ids changes — a finger lands, lifts, is
replaced, or the ids arrive reordered — every reference (orbit anchor, pair
centroid, pair distance) is re-read from the NEW set and **no orbit, pan or
zoom is emitted for that frame**. Movement is computed per pointer id, never
by list position. With three or more fingers, the first two to land steer.
Proved against the bug: re-introducing the old behaviour fails 7 tests (1→2)
and 3 (2→1).

## ORBIT

300° per short side of the viewport, yaw and pitch alike: a half turn at 3/5
of the width in portrait (the brief's ½–⅔), density-independent and unchanged
by rotation. 8 dp touch slop measured as displacement from the landing point
(jitter cannot accumulate past it); only the travel beyond the slop turns the
camera, so a drag never lurches as it starts; every one-finger phase starts
behind the slop again (the finger left after a pinch does not orbit on its
drift).

## PINCH ZOOM

Ratio of the pair's distance, clamped per frame to [0.8, 1.25] — reciprocal, so
out-and-back nets exactly zero; no zoom read below a 16 dp span (crossed or
merged contacts); NaN/∞ frames dropped; the camera's own distance clamp still
applies (tested finite and clamped over long sequences).

## PAN

The pair's centroid, in viewport heights, converted by `OrbitCamera.pan` with
distance, field of view and height: the point at the focus stays under the
fingers 1:1 (tested by projecting the old target into the new view).

## CAMERA TARGET CONTINUITY

Orbit changes yaw/pitch about the target; zoom changes distance to it; only
pan moves it; a pointer-count change never does (tested). No zoom-to-centroid
pivot was added (§21: stability first). One further jump was fixed on the way:
the frame callback read the Choreographer clock while transitions are stamped
with `System.currentTimeMillis()`, which froze a preset/frame transition at its
first pose until the next touch snapped it to the end; the frame callback now
uses the same clock.

## SECURITY

- **SSRF.** The API's URL fence (before queueing): https only, no credentials,
  port 443 only, no IP literal, no `localhost`/`.local`/`.internal`, ≤ 2048
  chars, and the host must be understood by a registered publisher adapter (in
  production only `archon.pl`). Inside the acquisition every hop is re-validated
  after DNS resolution (private, loopback, link-local, CGNAT, documentation and
  metadata ranges refused), redirects are followed manually (≤ 5), each body is
  capped at 24 MB, 120 assets, 20 s per fetch, media types allow-listed — the
  existing SourcePackage policy, unchanged. Tested: `file:`, `http:`, private and
  metadata IPs, credentials, ports, `localhost`, an unknown site, and a
  redirect from the publisher to a host resolving to 10.0.0.5 (refused on the
  hop, never requested).
- **Limits.** Body ≤ 4 KiB (413), JSON only (415), bounded queue (503 +
  `Retry-After`), per-client submission limit 6 / 10 min and read limit 1200 /
  10 min (429 + `Retry-After`); behind a trusted proxy the client is the LAST
  `X-Forwarded-For` entry (a forged leading entry does not escape the limit —
  tested); job time limit 15 min; worker heap limit.
- **Opaque ids, sanitised errors.** 128-bit random hex ids; any other id shape
  is 404; every error is a code and a sentence written by the service — no
  path, stack, host or environment in any response (checked over every body
  the API test suite received, and by the CI smoke on the bundle and the
  container). `X-Content-Type-Options`, `Referrer-Policy`, CSP
  `default-src 'none'`, HSTS when HTTPS is required.
- **No secret anywhere a client can see.** The API needs none. An optional
  server-side vision key would be read by the provider on the server only; the
  test suite sets a fake `ANTHROPIC_API_KEY` and proves it appears in no
  response; `http.ts` reads no environment variable. The APK's only build-time
  value is the service's public URL (architecture test); abuse control is
  entirely server-side, so nothing privileged is embedded in the APK.
- **No truth in the service.** The bundled production service contains no
  reference, candidate, benchmark, research, fixture or stage-artefact module,
  and no string naming the project it was tuned on (architecture test on the
  esbuild metafile and output). Results store no source image, no package, no
  reference.
- DNS rebinding between the check and the connect remains the documented
  limitation of `net.ts` (unchanged from BUILDAPP-02).

| unsupported URL / invalid link | the server's reason, before anything runs | the same (e2e) |
| source site timeout / unreachable | job FAILED `SOURCE_UNREACHABLE` with the reason | same |
| source changed during analysis | not possible within a job: each job fetches its sources once into its own scratch cache and seals them as one package; a later change shows up as different provenance hashes (see the Marcówki comparison) | same |
| job failed | the job's code and reason | same |
| result incompatible | hash mismatch / not a scene / too large: refused, nothing written | model hash mismatch: not opened |
| user cancels | CANCELLED, stage marked | same |
| service restarted mid-job | `SERVICE_RESTARTED`, run it again | same |

Nothing waits forever: every poll path ends in a terminal state, a failure, or a
retry with a stated delay. The bundled scenes need no network at all.

## KNOWN LIMITATIONS

- **The service is not deployed** (above). Until it is, the phone can analyse a
  link only against a service someone runs and gives it the https address of.
- **Nothing was run on a phone** in this stage: the gesture fix and the Analyzer
  screen are proved by JVM tests and a successful APK build, not on a device.
  The owner's phone review is the final gate for both (§23).
- An analysis of a real project takes 2–3 minutes, 85 % of it reading the
  drawings; the queue runs one job at a time by default
  (`ANALYZER_CONCURRENCY`).
- The publisher's page is not byte-stable, so two analyses of the same URL give
  the same building but different provenance hashes (package, graph, candidate).
- Only one publisher adapter exists (`archon.pl`); any other site is refused
  with `UNSUPPORTED_PUBLISHER`.
- The in-process executor (dev, tests) cannot interrupt a synchronous stage; it
  releases the job at once and the run stops at its next checkpoint. Production
  uses worker threads, which are terminated.
- Job ids are bearer-like: anyone with an id can read that job's result. They
  are 128-bit random and never listed; results expire after 72 h.
- DNS rebinding between the address check and the connection (the existing
  `net.ts` limitation).
- No vision provider runs by default; the result says `DETERMINISTIC_ONLY`.
- Progress has two plateaus on a real project: while the page's addresses are
  fetched (the total is not known in advance, so the bar holds at 0 % and the
  detail counts addresses) and while printed dimensions are read (about a
  minute, no countable units, the bar holds at ~63 %). Honest, but slow-looking.
