## ANALYZER APPLICATION SERVICE

`packages/analysis-service` (`@buildapp/analysis-service`):

- `runAnalysis(input, options)` with `input` = `{kind: 'URL', url}` or
  `{kind: 'PACKAGE', pkg, graph?}`, and `runLinkAnalysis({url, jobId, options,
  signal, progress})` — the brief's signature — over it.
- One path: `acquireSourcePackage` (SSRF-guarded, adapters the caller
  registers) → classification gate (a page with no plan and no elevation stops
  here, `NO_DRAWINGS`) → `analyzeSourcePackage` (deterministic CV; a vision
  provider only if the server configures one) → `extractMetricEvidence` →
  `reconstructV2` → `verifyReplay` → `compileBuilding` → `buildMobileSceneBundle`
  → round-trip `loadBundle` → `geometryClosureAudit`.
- Result (`src/result.ts`): `jobId, sourceUrl, canonicalUrl, title, label,
  modelId, sourcePackageHash, observationGraphHash, metricEvidenceHash,
  candidateHash, modelHash, modelSha256, sceneContentHash, sceneSha256,
  sceneBytes, counts, quality {levels L0/L1/L2, byFamily}, unresolved[],
  warnings[], vision {mode, provider, attempted, accepted}, verification
  {replay, residuals, residualsOutsideTolerance, closure}, analyzer,
  startedAt, completedAt, candidate, model, scene`. `summaryOf` drops the three
  heavy members for the API's `/result`.
- **Identity from the source alone.** Label and model id are part of the model
  and so of its hash; they derive from the package (`<title> (analysis)`,
  `m-analysis-<publisher code>`) — never from the job id or the clock — so one
  sealed input gives one set of hashes however it is run. The page title's
  boilerplate is stripped by an optional adapter hook (`displayTitle`), which is
  display only and changes no package hash.
- **Progress** is the position in the pipeline (`src/stages.ts`): nine stages,
  weights read off the real run below, per-drawing progress while reading the
  drawings, a hook at each solver phase (`reconstructV2({onPhase})`), and
  nothing on a timer. Monotone by construction.
- **Cancellation**: an `AbortSignal` checked between stages, on every byte read
  and inside every fetch (combined with the fetch's own timeout).
- **Errors** leave the service as a code and a sentence about the source:
  `INVALID_URL, UNSUPPORTED_PUBLISHER, SOURCE_REFUSED, SOURCE_UNREACHABLE,
  NO_DRAWINGS, ANALYSIS_FAILED, TIMEOUT, CANCELLED`. An unexpected exception
  becomes a fixed sentence, because its own text may carry a path.

## ANALYZER HTTP API

`apps/analyzer-api`, contract `docs/ANALYZER_API.md`. node:http only.

- `GET /health` — service, analyzer versions, publishers, vision mode, queue.
- `POST /v1/analyses {url}` → `202 {jobId, status: "QUEUED"}` + `Location`.
  Refusals before queueing: 400 `BAD_REQUEST`/`INVALID_URL`, 413, 415,
  422 `UNSUPPORTED_PUBLISHER`, 429 `RATE_LIMITED` (+`Retry-After`),
  503 `QUEUE_FULL`.
- `GET /v1/analyses/:id` — status, `progress`, current `stage` with detail, all
  nine `stages[]` with state and timestamps, `error`, a short `result`, links.
- `GET …/result` (summary with every hash), `…/scene` (exact bytes;
  `ETag`/`X-Content-SHA256`; 304 on `If-None-Match`), `…/model`,
  `…/candidate`; 409 `NOT_READY`, 410 `GONE` for a failed job.
- `DELETE /v1/analyses/:id` — cancel (a running worker is terminated).
- Statuses exactly the brief's thirteen.

Tests: `apps/analyzer-api/test/api.test.ts` (41) over a real socket and

## JOB STORE

`AnalysisJobStore` (`create, get, update, saveResult, loadResult, openResult,
list, delete, workspace, clearWorkspace`), implemented by `FileJobStore`: one
directory per job, every write to a temp file renamed into place, updates to
one job serialised in call order, a job id reaching a path only after matching
`^[0-9a-f]{32}$`. On start, a job left running by a previous process is marked
`FAILED / SERVICE_RESTARTED` (its worker is gone) and its scratch removed.
Results stay downloadable across a restart (tested). Finished jobs are swept
after `ANALYZER_RESULT_TTL_HOURS` (72) and beyond `ANALYZER_MAX_STORED_JOBS`
(200). Stored per job: `job.json`, and on success `result.json`, `scene.json`,
`model.json`, `candidate.json` — no source image, no package, no reference.

## JOB ISOLATION

- Each job runs in a **worker thread** of its own (`WorkerExecutor`, production)
  with a heap limit: the solver's long synchronous stretches never block the
  server (tested: `/health` answered in < 750 ms throughout a job, typically a
  few ms), and cancel/timeout terminate the thread (tested with a job that hangs
  forever inside it).
- Each job gets an **empty byte cache in its own scratch directory**, removed
  when the job ends — success, failure, cancel or timeout (all four tested).
- Two different URLs in sequence on one service, no restart: both complete,
  different candidates, the second fetched only its own sheets; the same URL
  again fetches everything again and gives the same building (tested). Two jobs
  side by side in two threads (tested).
- Artifact names are the job id and a fixed file name; nothing global.

## GESTURE ROOT CAUSE

`Viewport.kt` kept `previousCentroid` and `previousSpread` across a change in
the pointer set. When a second finger landed, the next frame compared the
two-finger centroid with the one-finger position (a pan of half the finger
distance) and the new spread with 0 or the old spread (a zoom). The reverse on
lift. The travel accumulator also mixed pan and spread change, and the orbit
gain was per pixel (0.32°/px: 346° per width at 1080 px, 461° at 1440 px).

## GESTURE REDUCER

`apps/android/app/src/main/java/com/buildplan/preview/camera/CameraGesture.kt`:
`CameraGestureTracker`, a pure state machine (no Android or Compose import).
Samples in (`Frame(pointers with ids, timeMs, width, height, density)` or
`Cancel`), semantic actions out (`Began, Orbit(dYaw, dPitch), Pan(right, up in
viewport heights), Zoom(scale), Tap, DoubleTap`). `Viewport.kt` only
translates Compose events into samples and actions into the existing view-model
calls; a system cancel (all pointers released at once, already consumed) is
recognised as `Cancel`.

## POINTER REBASE

Whenever the ordered list of pressed ids changes — a finger lands, lifts, is
replaced, or the ids arrive reordered — every reference (orbit anchor, pair
centroid, pair distance) is re-read from the NEW set and **no orbit, pan or
zoom is emitted for that frame**. Movement is computed per pointer id, never
by list position. With three or more fingers, the first two to land steer.
Proved against the bug: re-introducing the old behaviour fails 7 tests (1→2)
and 3 (2→1).

## ORBIT

300° per short side of the viewport, yaw and pitch alike: a half turn at 3/5
of the width in portrait (the brief's ½–⅔), density-independent and unchanged
by rotation. 8 dp touch slop measured as displacement from the landing point
(jitter cannot accumulate past it); only the travel beyond the slop turns the
camera, so a drag never lurches as it starts; every one-finger phase starts
behind the slop again (the finger left after a pinch does not orbit on its
drift).

## PINCH ZOOM

Ratio of the pair's distance, clamped per frame to [0.8, 1.25] — reciprocal, so
out-and-back nets exactly zero; no zoom read below a 16 dp span (crossed or
merged contacts); NaN/∞ frames dropped; the camera's own distance clamp still
applies (tested finite and clamped over long sequences).

## PAN

The pair's centroid, in viewport heights, converted by `OrbitCamera.pan` with
distance, field of view and height: the point at the focus stays under the
fingers 1:1 (tested by projecting the old target into the new view).

## CAMERA TARGET CONTINUITY

Orbit changes yaw/pitch about the target; zoom changes distance to it; only
pan moves it; a pointer-count change never does (tested). No zoom-to-centroid
pivot was added (§21: stability first). One further jump was fixed on the way:
the frame callback read the Choreographer clock while transitions are stamped
with `System.currentTimeMillis()`, which froze a preset/frame transition at its
first pose until the next touch snapped it to the end; the frame callback now
uses the same clock.
